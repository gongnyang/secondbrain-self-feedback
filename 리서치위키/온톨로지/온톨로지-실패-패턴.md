# 온톨로지 실패 패턴과 예방 규칙

| 실패 | 내용 | 예방 | 출처 |
|---|---|---|---|
| 과설계 | 실제 질문에 필요 없는 타입까지 추가 | 핵심 질문 10개를 먼저 정함. 타입 7개 이하. 새 타입은 사례 3건 이상일 때만 | https://kindatechnical.com/knowledge-graphs/how-to-design-an-ontology-step-by-step.html , https://blog.metaphacts.com/semantic-knowledge-modeling-best-practices |
| 가진 데이터부터 모델링 | 범위가 지나치게 넓어짐 | 유스케이스(보고 검토) 하나에서 시작 | https://info.stardog.com/questions-to-ontology |
| 용어 불일치 | 같은 것을 다르게 부름 | 용어 파일 하나를 정본으로. 동의어·금칙어 명시. 스킬이 정본 용어로 바꾸게 함 | (제안) |
| 스키마 드리프트, 인덱스 노후화 | 낡은 인덱스는 없는 것보다 나쁨 | 타입별 필수 키를 스키마 파일에 정의. lint로 누락 키·깨진 링크·고아 노트 점검. 스키마 변경은 log에 기록 후 반영 | https://zby.github.io/commonplace/sources/karpathy-llm-wiki.ingest/ , https://community.obsidian.md/plugins/propsec |
| 인스턴스와 클래스 혼동 | 특정 사례를 타입으로 만듦 | 타입 추가 전 "이게 종류인가, 한 건인가" 확인 | https://kindatechnical.com/knowledge-graphs/how-to-design-an-ontology-step-by-step.html |
| LLM이 기준을 직접 수정 | 승인 없이 기준이 바뀜 | 제안 → 확인 후 실행 → [[승인-게이트]] | (제안, 위험 자체는 미확인) |
